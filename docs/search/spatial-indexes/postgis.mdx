# PostGIS

Для ознакомления с пространственными индексами используется расширение PostgreSQL – PostGIS,
ввиду его популярности.
Для более глубокого ознакомления с PostGIS рекомендуется [воркшоп](https://postgis.net/workshops/postgis-intro/).

Эта страница — практический и системный «двойник» теоретического разбора в заметке [R-tree](./r-tree.mdx). Там описано, *как устроена* структура данных (MBR, варианты R-дерева, алгоритмы разделения и сложность); здесь показано, *как пространственный индекс реально применяется* в СУБД. PostGIS не реализует отдельный тип индекса для геометрии — он опирается на штатный механизм PostgreSQL **GiST** (Generalized Search Tree), который для пространственных типов ведёт себя как R-дерево. Ниже разбирается, как именно запросы используют такой индекс: какие операторы его «включают», почему планировщик иногда от него отказывается и какие альтернативы существуют.

## Работа с пространственными данными

Загруженный набор данных представляет собой данные о переписи населения
в городе Нью-Йорк с привязкой этих данных к пространственным зонам.

Рассмотрим пространственные данные для таблицы `nyc_census_blocks`, представляющей информацию о переписных блоках Нью-Йорка:

```sql
SELECT geom from nyc_census_blocks;
```

А также для таблицы `nyc_subway_stations`, содержащей информацию о станциях метро города:

```sql
SELECT geom from nyc_subway_stations;
```

Далее воспользуемся функцией `ST_Contains` расширения PostGIS, позволяющей
определять, содержит ли одна геометрия другую.

Для примера найдем все переписные блоки, в которых есть станции метро, название которых начинается с `B`:

```sql
SELECT blocks.geom
 FROM nyc_census_blocks blocks
 JOIN nyc_subway_stations subways
 ON ST_Contains(blocks.geom, subways.geom)
 WHERE subways.name LIKE 'B%';
```

Рассмотренные таблицы уже содержат пространственные индексы.

Для наглядности удалим один из них и оценим время выполнения предыдущего запроса.

```sql
DROP INDEX nyc_census_blocks_geom_idx;
```

Время выполнения запроса без индекса составило 1 сек. 269 мс.
(конкретное значение может отличаться в зависимости от машины, на которой выполняется запрос).

Добавим индекс обратно:

```sql
CREATE INDEX nyc_census_blocks_geom_idx
  ON nyc_census_blocks
  USING GIST (geom);
```

Время выполнения того же запроса с индексом составило 100 мс.

Хотя таблица `nyc_census_blocks` сравнительно небольшая, разница во времени значительна.
С ростом объёма данных эффект от индекса будет только увеличиваться.

## Двухфазная обработка пространственных запросов (filter + refine)

Ускорение, наблюдаемое в примере выше, объясняется тем, что пространственный запрос выполняется в две фазы. Это ключевая идея, без которой невозможно понять поведение пространственного индекса.

Пространственный индекс хранит **не сами геометрии, а только их ограничивающие прямоугольники** — bounding box (двумерный частный случай — MBR; определение и роль MBR подробно разобраны в заметке [R-tree](./r-tree.mdx)). Точная геометрия полигона из сотен вершин в индексе не лежит — там лежат лишь четыре числа `(x_min, y_min, x_max, y_max)`.

Отсюда два этапа [[6](#ref-postgis-indexing)] [[7](#ref-postgis-workshop)]:

- **Этап фильтрации** (*primary filter*, первичный фильтр). Индекс по bounding box быстро находит набор геометрий-кандидатов, прямоугольники которых удовлетворяют условию запроса. Это дёшево: сравниваются прямоугольники, а не сложные фигуры. Воркшоп формулирует это так: сначала отвечаем на вопрос «какие прямоугольники пересекают искомый прямоугольник» с помощью индекса (очень быстро) [[7](#ref-postgis-workshop)].

- **Этап уточнения** (*secondary filter*, вторичный фильтр). На геометриях-кандидатах выполняется точный предикат вычислительной геометрии (например, действительно ли полигон содержит точку). Эта проверка нагружает процессор, но запускается **только для тех объектов, которые прошли первый тест** [[7](#ref-postgis-workshop)] — то есть для небольшого подмножества, а не для всей таблицы.

Связь первой фазы с индексом обеспечивает оператор `&&`. Для геометрий `a && b` истинно, когда **bounding box `a` и bounding box `b` перекрываются или соприкасаются** [[6](#ref-postgis-indexing)]. Именно этот оператор умеет отвечать GiST-индекс.

Функции-предикаты вроде `ST_Contains` и `ST_Intersects` внутри себя комбинируют дешёвое индексное условие `&&` по bounding box и дорогой точный предикат. Поэтому запрос из лабораторной работы выше

```sql
SELECT blocks.geom
 FROM nyc_census_blocks blocks
 JOIN nyc_subway_stations subways
 ON ST_Contains(blocks.geom, subways.geom)
 WHERE subways.name LIKE 'B%';
```

фактически выполняется так: индекс по `&&` сначала отбирает пары блок/станция, чьи прямоугольники пересекаются (первичный фильтр), и лишь затем для них вычисляется точное `ST_Contains` (вторичный фильтр). Удаление индекса в примере отключает первичный фильтр — и точная проверка вынужденно прогоняется по всем парам, отсюда и рост времени.

## GiST как обобщённый фреймворк

PostGIS не пишет собственное R-дерево с нуля. Вместо этого он подключается к механизму **GiST** (Generalized Search Tree), предложенному в работе Hellerstein, Naughton и Pfeffer на VLDB 1995 [[1](#ref-gist-paper)]. GiST — это **расширяемый шаблон сбалансированного дерева поиска**: сама древовидная механика (поиск, вставка, разделение страниц, балансировка) реализована один раз в ядре PostgreSQL, а конкретное «значение» дерева задаётся набором пользовательских функций для типа данных и класса операторов. Для пространственного класса операторов это дерево становится R-деревом (теория самого R-дерева, включая алгоритмы разделения, разобрана в заметке [R-tree](./r-tree.mdx) — здесь мы их не повторяем).

Расширение типа данных под GiST сводится к реализации набора **опорных функций** (support methods). По документации PostgreSQL [[2](#ref-pg-gist)]:

- `consistent` — проверяет, может ли запись индекса удовлетворять условию запроса (обязательная);
- `union` — строит обобщающую запись (bounding box), покрывающую группу записей (обязательная);
- `penalty` — оценивает «штраф» за добавление записи в данное поддерево, управляя выбором ветви при вставке (обязательная);
- `picksplit` — определяет, как разделить переполненную страницу на две (обязательная);
- `same` — проверяет равенство двух записей индекса (обязательная);
- `compress` — приводит значение к компактному представлению, хранимому в индексе (необязательная; если опущена, значения хранятся без изменений; для геометрии в индекс кладётся именно bounding box);
- `distance` — возвращает расстояние от запроса до записи и **включает упорядоченные сканы — поиск ближайших соседей (KNN)** (необязательная; см. раздел про `<->` ниже).

Для пространственных типов PostGIS реализует эти функции так, что получается R-дерево поверх GiST: `union` строит охватывающий прямоугольник, `picksplit` распределяет прямоугольники между страницами, `consistent` отсекает поддеревья по bounding box. Внутренние узлы хранят MBR, поиск использует ту самую двухфазную фильтрацию.

## Классы операторов GiST (opclasses)

Один тип данных может иметь несколько **классов операторов** (operator class, opclass). Класс операторов определяет, какие именно операторы способен обслуживать индекс и в каком пространстве (2D, n-мерное, географическое). PostGIS предоставляет три основных класса для GiST [[6](#ref-postgis-indexing)]:

- `gist_geometry_ops_2d` — класс по умолчанию для типа `geometry`. Работает с двумерным bounding box и поддерживает операторы `&&`, `<->` и другие 2D-операторы. Именно он создаётся обычным `USING GIST (geom)`.
- `gist_geometry_ops_nd` — n-мерный класс для `geometry`. Работает с n-мерным bounding box и оператором перекрытия `&&&`. Указывается явно:

  ```sql
  CREATE INDEX nyc_census_blocks_geom_nd_idx
    ON nyc_census_blocks
    USING GIST (geom gist_geometry_ops_nd);
  ```

- `gist_geography_ops` — класс по умолчанию для типа `geography`; используется автоматически при `USING GIST (geog)` над столбцом типа `geography` и поддерживает `&&` для географических данных.

Класс операторов критичен: индекс с 2D-классом не обслужит n-мерный запрос (по `&&&`) и наоборот, а индекс по `geography` не подойдёт для `geometry`. Если оператор в запросе не входит в набор класса операторов индекса, индекс попросту не будет использован.

| Класс операторов        | Тип        | Индексируемые операторы (пример) |
|-------------------------|------------|----------------------------------|
| `gist_geometry_ops_2d`  | `geometry` | `&&`, `<->`                      |
| `gist_geometry_ops_nd`  | `geometry` | `&&&`                            |
| `gist_geography_ops`    | `geography`| `&&`                             |

(Таблица иллюстративная; полный перечень операторов каждого класса см. в индексном разделе руководства PostGIS [[6](#ref-postgis-indexing)].)

## Поиск ближайших соседей (KNN, оператор `<->`)

Помимо «попадания в область», частой задачей является поиск ближайших объектов: «k ближайших станций метро к заданной точке». За это отвечает оператор расстояния `<->`: `a <-> b` возвращает 2D-расстояние между геометриями [[8](#ref-postgis-knn)].

Главная ценность `<->` в том, что в секции `ORDER BY ... LIMIT k` он **обслуживается индексом** (index-assisted nearest-neighbour). Это работает благодаря опорной функции `distance` класса операторов GiST [[2](#ref-pg-gist)]: при обходе дерева для каждого узла вычисляется нижняя граница расстояния до его bounding box, что позволяет извлекать кандидатов в порядке возрастания расстояния и остановиться, как только набрано `k` объектов, не сканируя таблицу целиком.

Пример: пять станций метро, ближайших к точке (Бруклинский музей, координаты в проекции набора данных, SRID 26918):

```sql
SELECT name, geom <-> ST_SetSRID(ST_MakePoint(586477, 4504484), 26918) AS dist
  FROM nyc_subway_stations
 ORDER BY geom <-> ST_SetSRID(ST_MakePoint(586477, 4504484), 26918)
 LIMIT 5;
```

Здесь важны два условия индексного ускорения [[8](#ref-postgis-knn)]:

- сравниваемая точка должна быть **константой** (а не выражением из подзапроса/CTE), иначе планировщик не сможет применить kNN-обход индекса;
- `<->` должен стоять именно в `ORDER BY` — в `WHERE` он индексом не ускоряется.

На этапе обхода индекс оперирует расстоянием до bounding box (то есть до прямоугольников), а точное расстояние между геометриями уточняется на кандидатах с перепроверкой (recheck) — это снова та же двухфазная модель, но для упорядочивания, а не для фильтрации.

## Когда планировщик НЕ использует пространственный индекс

Наличие индекса не гарантирует его использование. Планировщик PostgreSQL выбирает план по оценке стоимости, и в ряде ситуаций пространственный индекс не применяется. Самое надёжное средство диагностики — `EXPLAIN (ANALYZE)`, который показывает фактически выбранный план и реальное время [[5](#ref-pg-planner)].

**(a) Предикат не разворачивается в индексное условие `&&`.** Классический пример — фильтр по расстоянию через `ST_Distance`:

```sql
-- индекс НЕ используется: ST_Distance вычисляется на результате
SELECT * FROM nyc_subway_stations
 WHERE ST_Distance(geom, :point) < 500;
```

`ST_Distance` — это функция, вычисляемая уже на строках; она не добавляет к запросу bbox-условие `&&`, а значит, индексу «не за что зацепиться». Правильный вариант — `ST_DWithin`, который воркшоп прямо называет функцией, дающей «within a distance»-запросам ускорение от индекса [[7](#ref-postgis-workshop)] [[9](#ref-postgis-dwithin)]:

```sql
-- индекс используется: ST_DWithin добавляет bbox-условие &&
SELECT * FROM nyc_subway_stations
 WHERE ST_DWithin(geom, :point, 500);
```

`ST_DWithin` внутри себя добавляет индексное условие на пересечение bounding box (геометрия против прямоугольника, расширенного на радиус), и только затем выполняет точную проверку расстояния — поэтому он совместим с двухфазной моделью, а `ST_Distance < x` нет.

**(b) Низкая селективность / маленькая таблица.** Если условие пропускает большую долю строк или таблица невелика (как `nyc_census_blocks`, про которую в лабораторной работе сказано, что она «сравнительно небольшая»), последовательное сканирование может оказаться дешевле обхода индекса, и планировщик осознанно выберет seq scan.

**(c) Устаревшая статистика.** Планировщик опирается на статистику распределения данных. Если она устарела (например, после массовой загрузки), оценки селективности будут неверны и план — неоптимален. Решение — выполнить `ANALYZE`; для пространственных столбцов PostGIS поддерживает собственную статистику геометрии и собственные оценщики селективности предикатов [[6](#ref-postgis-indexing)].

**(d) Несоответствие SRID, типа или класса операторов.** Сравнение `geometry` с `geography`, 2D-запрос против nd-индекса (или наоборот), несовпадение SRID — всё это мешает планировщику применить индекс, потому что оператор запроса не входит в класс операторов индекса (см. раздел про opclasses).

**(e) Функциональное преобразование индексируемого столбца.** Если в предикате столбец обёрнут функцией, например `ST_Transform(geom, 4326)`, обычный индекс по `geom` не подходит: индексируется `geom`, а условие применяется к *результату функции*. Помочь может только функциональный (выражательный) индекс по тому же выражению:

```sql
CREATE INDEX ON nyc_subway_stations USING GIST (ST_Transform(geom, 4326));
```

## Альтернативные типы индексов (SP-GiST, BRIN)

GiST — основной, но не единственный пространственный индекс в PostgreSQL.

- **SP-GiST** (Space-Partitioned GiST) — фреймворк для **несбалансированных деревьев на основе разбиения пространства**: квадродеревьев (quadtree), k-d деревьев, radix-деревьев [[3](#ref-pg-spgist)]. В отличие от GiST/R-дерева, разбиения **не перекрываются**, поэтому SP-GiST особенно хорош для **точечных данных** и непересекающихся областей. Для типа `point` есть классы `quad_point_ops` (квадродерево, по умолчанию) и `kd_point_ops` (k-d дерево); оба поддерживают и KNN через `<->`. Для равномерно распределённых точек SP-GiST может обгонять GiST за счёт отсутствия перекрытий между ветвями.

- **BRIN** (Block Range INdex) — **блочно-диапазонный** индекс: для каждого диапазона физически соседних страниц хранится сводка (для геометрических типов — охватывающий bounding box) [[4](#ref-pg-brin)]. BRIN крошечный и потерянный (lossy): он лишь отсекает диапазоны страниц, после чего требуется перепроверка строк. Он выигрывает на **очень больших таблицах, физически отсортированных по пространственной близости** (когда близкие в пространстве объекты лежат и на соседних страницах диска), обменивая точность на минимальный размер. В ядре PostgreSQL геометрические типы поддерживаются классом `box_inclusion_ops`; PostGIS дополнительно предоставляет BRIN-классы для `geometry`. Если же данные физически не упорядочены по близости, выигрыш BRIN исчезает.

Кратко: GiST — разумный выбор по умолчанию для произвольной геометрии; SP-GiST бывает быстрее на чисто точечных непересекающихся данных; BRIN оправдан на огромных, естественно отсортированных по пространству таблицах, где важен размер индекса.

## Стоимость двухфазной модели

Двухфазную модель удобно держать в голове как простую формулу стоимости пространственного запроса:

```
стоимость_фильтрации ~ высота_дерева
стоимость_уточнения  ~ число_кандидатов × стоимость_точного_предиката
общая_стоимость      ≈ стоимость_фильтрации + стоимость_уточнения
```

Первичный фильтр (обход GiST по bounding box) стоит порядка высоты дерева — то есть логарифмичен от числа объектов (см. оценки сложности R-дерева в заметке [R-tree](./r-tree.mdx)). Вторичный фильтр линеен по числу кандидатов, прошедших первый этап, и пропорционален цене точного геометрического предиката. Отсюда главный вывод: производительность определяется **селективностью bbox-фильтра** — чем меньше прямоугольников-кандидатов он пропускает дальше, тем меньше дорогих точных проверок выполняется. Именно поэтому усилия по оптимизации (от выбора класса операторов до использования `ST_DWithin` вместо `ST_Distance`) направлены на то, чтобы как можно больше работы выполнял дешёвый первичный фильтр.
