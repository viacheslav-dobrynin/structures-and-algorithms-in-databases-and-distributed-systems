# Неизменяемые и персистентные структуры данных

## Мотивация

**Неизменяемые** (immutable) структуры данных не меняют своё наблюдаемое состояние после создания: любое «изменение» порождает новое значение, оставляя старое нетронутым. Это свойство ценно сразу по нескольким причинам:

- **Тривиальная потокобезопасность чтения без блокировок.** Если объект не мутируется, его можно безопасно читать из любого числа потоков одновременно — синхронизация не нужна, потому что нет гонок «читатель против писателя».
- **Снимки и путешествие во времени (time-travel).** Старые версии остаются доступными, что даёт версионирование, undo/redo и воспроизводимость состояния на любой момент.
- **Снимки для MVCC.** Транзакция может работать с согласованным неизменным снимком данных, пока остальные продолжают вносить изменения (см. [Связь с базами данных и распределёнными системами](#связь-с-базами-данных-и-распределёнными-системами)).
- **Функциональное программирование.** Неизменяемость — фундамент чистоты функций: отсутствие побочных эффектов упрощает рассуждение о коде, мемоизацию и распараллеливание.

Центральное противоречие, вокруг которого построена эта страница, такое: наивная неизменяемость требует копировать всю структуру при каждом изменении — `O(n)` времени и памяти на операцию. Если каждое добавление элемента в список из миллиона элементов копирует весь миллион, неизменяемость практически бесполезна. Главная тема страницы — как сделать **версионируемые** обновления дешёвыми за счёт **структурного разделения** (structural sharing): новая версия переиспользует неизменные части старой, а копирует лишь то, что действительно изменилось.

Неизменяемость — это альтернативный путь к безопасному параллелизму. Lock-free структуры (см. [Конкурентные структуры данных без блокировок](../lock-free/concurrent-data-structures.mdx)) избегают блокировок, выполняя атомарные read-modify-write операции над **изменяемой** структурой; персистентные структуры избегают блокировок иначе — они **никогда не мутируют**, и читатель просто держит неизменный снимок. Детали CAS, hazard pointers и RCU здесь не повторяются — см. указанную страницу.

## Иммутабельность и персистентность: определения

Два понятия тесно связаны, но не тождественны.

- **Иммутабельность (immutability)** — свойство объекта: его наблюдаемое состояние никогда не изменяется после создания.
- **Персистентность (persistence)** в смысле Driscoll, Sarnak, Sleator, Tarjan [[1](#ref-dsst)] — свойство структуры: операция обновления порождает **новую версию**, а **предыдущие версии остаются доступными** для запросов. (Это не та «персистентность», что означает сохранение на диск; здесь речь о сохранении истории версий в памяти.)

Связь между ними прямая: персистентность эффективно реализуется через структурное разделение неизменных частей. Если части старой версии неизменны, новая версия может ссылаться на них без копирования — именно неизменяемость делает разделение безопасным.

DSST вводят таксономию по тому, какие версии можно запрашивать и изменять [[1](#ref-dsst)]:

| Вид персистентности | Запрос версий | Обновление версий | Топология версий |
|---|---|---|---|
| Частичная (partial) | любая версия | только последняя | линейная цепочка |
| Полная (full) | любая версия | любая версия | дерево версий |
| Конфлюэнтная (confluent) | любая версия | любая + слияние версий | ориентированный ациклический граф (DAG) |
| Функциональная (functional) | любая версия | любая версия (чисто функционально) | дерево/DAG, без разрушающего присваивания |

Функциональная персистентность — частный случай полной, в котором запрещено разрушающее присваивание: все структуры неизменны, что автоматически делает их полностью персистентными. Конфлюэнтная персистентность сложнее остальных, потому что слияние версий может приводить к экспоненциальному росту, если не применять специальные приёмы.

## Структурное разделение

**Структурное разделение** — это переиспользование неизменных узлов старой версии в новой. Рассмотрим сбалансированное дерево глубины `d`. Обновление одного листа затрагивает только узлы на пути от корня к этому листу — таких узлов `O(d)`. Приём **path copying** («копирование пути») копирует именно эти `O(d)` узлов, перенаправляя их указатели, а все поддеревья **вне пути** остаются общими: новый корень ссылается на них по ссылке, без копирования.

Важно отличать структурное разделение от наивного **copy-on-write (COW)**:

- **Copy-on-write в наивной форме** копирует **весь объект** при первой записи — `O(n)`. Разделение есть лишь до первой записи; как только нужно изменить хоть один элемент, копируется всё.
- **Структурное разделение** копирует **только путь** изменения — `O(log n)` для сбалансированного дерева, — а нетронутые поддеревья остаются общими навсегда, в том числе после записи.

Иными словами, COW разделяет объект целиком до первой мутации, а структурное разделение разделяет на уровне отдельных узлов и сохраняет разделение даже после обновлений. Именно поэтому персистентные структуры платят `O(log n)`, а не `O(n)`, за версию. (Заметим, что «умный» COW на уровне страниц/узлов — это уже по сути path copying; различие именно с наивным копированием объекта целиком.)

## Методы реализации персистентности

DSST описывают три общих способа сделать произвольную связную структуру персистентной [[1](#ref-dsst)].

- **Fat node (толстый узел).** Каждый узел хранит **список модификаций** в виде пар `(версия, значение)`. При записи поля не перезаписывается, а к узлу добавляется новая запись с номером версии. Запрос поля в заданной версии выполняется бинарным поиском по списку модификаций — `O(log m)`, где `m` — число модификаций узла. Память на обновление — `O(1)` (одна запись), но запросы замедляются логарифмически.
- **Path copying (копирование пути).** При изменении узла копируется он сам и все узлы на пути до корня; для каждой версии хранится свой корень. Запрос идёт по нужному корню без всякого замедления (`O(1)` накладных расходов на шаг), но обновление стоит `O(p)` времени и памяти, где `p` — длина пути от изменяемого узла до корня. Для деревьев `p = O(log n)`.
- **Node copying / node splitting (копирование узлов с расщеплением).** Гибрид: узел, как в fat node, хранит ограниченное число дополнительных указателей-модификаций; при переполнении узел «расщепляется» — создаётся его копия, и модификация распространяется к предкам. Главный результат DSST: при **ограниченной входящей степени** (in-degree) узлов этот метод даёт `O(1)` амортизированных накладных расходов по памяти на каждое изменение поля **и** `O(1)` замедление запроса. Неформально: расщепления случаются достаточно редко (амортизированно константу раз на изменение), потому что каждое расщепление освобождает место под несколько последующих модификаций, а ограниченная входящая степень не даёт каскаду расщеплений распространяться слишком широко.

Path copying проще всего реализовать и он естественно подходит для деревьев, поэтому именно он лежит в основе большинства практических персистентных структур (см. ниже).

## Персистентные списки и стеки

Простейшая персистентная структура — **cons-список** (односвязный список) — он же неизменяемый стек. Операции:

- **`push(x, lst)`** — создать новый узел `cons(x, lst)`, указывающий на старый список как на хвост; `O(1)`.
- **`pop(lst)`** / **`peek(lst)`** — вернуть голову и хвост существующего списка; `O(1)`, без всякого копирования.

Хвост никогда не копируется — новая голова просто ссылается на него. Поэтому множество версий разделяет один и тот же «хребет» (spine).

Рассмотрим конкретный пример. Пусть есть базовый список из двух узлов:

```text
v1 = [2, 1]:     2 → 1 → nil
```

Теперь сделаем два независимых push поверх `v1`:

```text
v2 = push(3, v1) = [3, 2, 1]:   3 ┐
                                   ├→ 2 → 1 → nil
v3 = push(4, v1) = [4, 2, 1]:   4 ┘
```

Обе новые версии (`v2` и `v3`) разделяют **один и тот же** хвост `2 → 1 → nil`. Подсчёт узлов:

- хвост `{2, 1}` — 2 узла, общие для всех трёх версий;
- голова `3` — 1 новый узел (версия `v2`);
- голова `4` — 1 новый узел (версия `v3`).

Итого: **4 узла** физически хранят **3 версии** списка. Каждый push добавил ровно 1 узел вместо копирования всего списка. Это и есть «структурное разделение по ссылкам», на которое указывает страница про lock-free структуры: неизменяемый хвост можно безопасно разделять между версиями именно потому, что его никто не мутирует.

## Персистентные сбалансированные деревья

Для упорядоченных коллекций (множеств и отображений) применяют **персистентные сбалансированные деревья поиска** — например, красно-чёрные или весо-сбалансированные (weight-balanced) деревья — реализованные через path copying. Каждое обновление копирует только `O(log n)` узлов на пути от корня к точке изменения; старая версия остаётся полностью валидной со своим корнем.

| Операция | Время | Доп. память на версию |
|---|---|---|
| `lookup` | `O(log n)` | — |
| `insert` | `O(log n)` | `O(log n)` |
| `delete` | `O(log n)` | `O(log n)` |

Именно так устроены неизменяемые упорядоченные `Map`/`Set` в функциональных языках: модуль `Map` в OCaml и `Data.Map` в Haskell — это сбалансированные деревья с path copying, дающие персистентность «бесплатно» как следствие неизменяемости.

## HAMT

**HAMT** (Hash Array Mapped Trie) — персистентное хеш-отображение, предложенное Багвеллом в 2001 году [[3](#ref-hamt)]. Идея: построить трай (префиксное дерево), индексируемый не по символам ключа, а по **порциям хеша** ключа. Хеш разбивается на куски по 5 бит; каждый кусок (значение `0..31`) выбирает одну из 32 ветвей на очередном уровне — то есть ветвление равно 32.

Чтобы не хранить массив из 32 указателей в каждом узле (большинство из которых пусты), HAMT использует **битовую карту** (bitmap) присутствия детей: один 32-битный bitmap отмечает, какие из 32 позиций заняты, а сами указатели хранятся в компактном массиве только для присутствующих детей. Индекс ребёнка в этом массиве вычисляется как количество единичных битов в bitmap ниже нужной позиции — операцией **popcount**. Так узел занимает память пропорционально числу реальных детей, а не 32.

Глубина HAMT определяется тем, сколько 5-битных кусков хеша нужно, чтобы различить `n` ключей:

```text
глубина ≈ ceil(log32 n) = ceil(log2 n / 5)
```

Например, для `n = 10^6`:

```text
log2(10^6) ≈ 19.93
19.93 / 5 ≈ 3.99
ceil(3.99) = 4
```

То есть `log32(10^6) ≈ 4` — глубина дерева около 4 уровней. Обновление копирует только узлы на пути, то есть `O(log32 n)` узлов. HAMT лежит в основе персистентных хеш-отображений Clojure и Scala [[8](#ref-clojure)].

## Персистентные векторы (bit-partitioned tries)

Индексируемый массив (вектор) с произвольным доступом тоже можно сделать персистентным, организовав его как **bit-partitioned trie** — трай, в котором ключом служит сам целочисленный индекс. Персистентный вектор Clojure (создан Ричем Хикки на основе линии идей Багвелла об idealized hash tries — атрибуция в прозе, отдельной статьи нет) представляет собой дерево с ветвлением 32: биты индекса разбиваются на группы по 5, и каждая группа выбирает ребёнка на своём уровне.

Доступ и обновление по индексу стоят `O(log32 n)`. При ветвлении 32 это число почти постоянно для реалистичных размеров: дерево из четырёх уровней адресует до `32^4 = 1 048 576` элементов. Конкретно, для вектора в `10^6` элементов:

```text
32^4 = 1 048 576 ≥ 10^6   ⇒   глубина = 4
```

Обновление одного элемента копирует по одному узлу на каждом из 4 уровней пути — около **4 скопированных узлов на обновление**, остальное дерево разделяется по ссылкам.

**RRB-Trees** (Relaxed Radix Balanced Trees) Багвелла и Ромпфа [[4](#ref-rrb)] расширяют эту конструкцию «ослабленной» радиксной балансировкой: узлы могут быть заполнены не до конца, а в них хранится таблица размеров поддеревьев. Это позволяет выполнять **конкатенацию и расщепление** векторов за `O(log n)`, сохраняя при этом `O(log32 n)` доступ по индексу, чего обычный bit-partitioned вектор без относительно дорогой перестройки не умеет.

## Finger trees

**Finger tree** (Hinze & Paterson, 2006) [[5](#ref-fingertree)] — универсальная персистентная структура-последовательность. Она построена как 2-3 дерево с «пальцами» (finger) — кешированным доступом к обоим концам — и снабжена **моноидальной мерой** (аннотацией) в каждом узле. Меняя моноид, из одной и той же структуры получают разные абстракции: deque (доступ с двух концов), очередь с приоритетами (мера = максимум), последовательность с произвольным доступом (мера = размер), интервальное дерево и т. д.

| Операция | Время |
|---|---|
| Доступ/вставка/удаление с любого конца | `O(1)` амортизированно |
| Конкатенация | `O(log n)` |
| Расщепление | `O(log n)` |

## Амортизация и персистентность: проблема и решение Окасаки

Для амортизационного анализа применяют **метод банкира** (credits, кредиты) и **метод физика** (потенциал `Φ`). Базовая схема:

```text
амортизированная стоимость = фактическая стоимость + ΔΦ
```

где `ΔΦ` — изменение потенциала. Суммируя по последовательности операций, накопленные кредиты «оплачивают» дорогие операции за счёт дешёвых.

**Проблема.** Стандартный амортизационный анализ предполагает **единственную линейную последовательность** операций: каждая структура-результат используется ровно один раз как вход следующей операции. Персистентность это предположение ломает. Поскольку любая старая версия остаётся доступной, одну и ту же дорогую версию можно сделать стартовой точкой **много раз** («множество вариантов будущего», multiple futures). Каждое такое будущее заново запускает отложенную дорогую операцию и платит полную худшую стоимость — то есть накопленные кредиты «тратятся» более одного раза, и амортизационные оценки перестают быть верными. Классический пример — амортизированная очередь из двух стеков: если вызвать дорогую операцию «разворота» из одной и той же версии дважды, она выполнится дважды по полной цене.

**Решение Окасаки** [[2](#ref-okasaki)]: **ленивое вычисление с мемоизацией**. Дорогая работа оборачивается в **отложенное вычисление** (suspension); при первом форсировании результат вычисляется и **мемоизируется**. Тогда второй и последующие «варианты будущего», стартующие из той же версии, форсируют уже вычисленную (мемоизированную) suspension и платят `O(1)` вместо полной стоимости. Это восстанавливает амортизационные оценки в персистентном окружении. Для анализа таких структур Окасаки адаптирует метод банкира к ленивости через **дебеты** (debits): дебет — это отложенная, ещё не оплаченная работа, привязанная к suspension; оценка ограничивает, сколько дебетов может «висеть» прежде, чем suspension форсируется. На этой технике построены **banker's queue** и **real-time queue** Окасаки, а также общий приём **неявного рекурсивного замедления** (implicit recursive slowdown).

## Связь с базами данных и распределёнными системами

Идеи неизменяемости и персистентности пронизывают системы хранения и репликации.

- **MVCC и snapshot isolation.** Транзакция читает согласованный неизменный снимок данных, а новые версии строк добавляются, не перезаписывая старые, — это персистентность на уровне строк/страниц. (Подробный разбор MVCC через атомарные операции — на странице про [lock-free структуры](../lock-free/concurrent-data-structures.mdx); здесь повторного вывода нет.)
- **Append-only / copy-on-write B-деревья.** CouchDB использует append-only B+дерево: запись добавляет в конец файла новые узлы и новый корень, а старое дерево остаётся валидным — это даёт устойчивые к сбоям MVCC-чтения, потому что незавершённая запись не портит предыдущий корень [[6](#ref-couchdb)]. LMDB реализует COW B+дерево с одним писателем (single-writer MVCC): писатель копирует изменяемый путь к новому корню, а читатели работают со старым корнем и **никогда не блокируют писателя** и не блокируются им [[7](#ref-lmdb)]. Обе системы — это, по сути, path-copying персистентность, применённая к дисковым B-деревьям.
- **LSM-деревья.** SSTable неизменяемы по построению; compaction не правит существующие файлы, а создаёт новые неизменные файлы взамен старых. (Подробнее об LSM и фильтрах Блума — на соответствующих страницах; здесь без дублирования.)

Общая выгода для конкурентности: неизменяемые разделяемые структуры не требуют блокировок на чтение — читатель держит снимок, который никто не изменит у него «под руками».

## Сборка мусора и подсчёт ссылок

Структурное разделение означает, что один узел может принадлежать многим версиям одновременно. Поэтому освобождение памяти нетривиально: узел можно освободить, только когда он **недостижим ни из одной живой версии**. Удаление (отпускание ссылки на) версии освобождает лишь те узлы, которые после этого становятся недостижимы из всех оставшихся версий; узлы, ещё разделяемые с другими версиями, остаются жить.

Это требует автоматического управления памятью — **сборщика мусора (GC)** или **подсчёта ссылок (reference counting)**. Чисто функциональные неизменяемые структуры образуют **DAG без циклов** (новая версия ссылается только на уже существующие старые узлы, обратных ссылок нет), поэтому подсчёт ссылок здесь корректен и безопасен — проблема циклов, мешающая RC в общем случае, не возникает.

Именно поэтому HAMT и персистентные векторы естественно расцветают на платформах с трассирующим GC — JVM (Clojure, Scala) и CLR: разделяемые узлы освобождаются автоматически. В средах без GC — Rust (крейт `im`) или C++ — приходится явно использовать подсчёт ссылок (`Arc`/`shared_ptr`) либо epoch-based reclamation, чтобы корректно освобождать разделяемые узлы.

## Сложность

Сводная таблица; `n` — число элементов. «Доп. память на версию» — память, выделяемая одной операцией обновления сверх разделяемой части.

| Структура | Операция | Время | Доп. память на версию |
|---|---|---|---|
| Персистентный список/стек | `push` / `pop` / `peek` | `O(1)` | `O(1)` |
| Персистентное сбалансированное дерево | `lookup` / `insert` / `delete` | `O(log n)` | `O(log n)` |
| HAMT (хеш-отображение) | `lookup` / `insert` / `delete` | `O(log32 n)` ≈ const | `O(log32 n)` |
| Персистентный вектор | доступ / обновление по индексу | `O(log32 n)` ≈ const | `O(log32 n)` |
| RRB-Tree | конкатенация / расщепление | `O(log n)` | `O(log n)` |
| Finger tree | доступ с концов | `O(1)` амортизированно | `O(1)` амортизированно |
| Finger tree | конкатенация / расщепление | `O(log n)` | `O(log n)` |

Записи `O(log32 n) ≈ const` отражают, что при ветвлении 32 даже миллионы элементов дают глубину около 4 (см. разделы [HAMT](#hamt) и [Персистентные векторы](#персистентные-векторы-bit-partitioned-tries)), так что на практике доступ воспринимается почти как константный.
